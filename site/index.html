Route Protection Intent

Plugin and CLI: security-sidecar · GitHub Action: Route Protection Check

Documents the protection intent of each web route, so that even if the AI misses something, it can still be caught.

View on GitHub Playbook

Advice, not a firewall. A sidecar records intent and blocks nothing in its default annotate mode. It is not a secure-coding rule set or a linter: use /security-review and your own scanners for that.

The problem

An AI assistant writes a route and gets the protection right, or quietly gets it wrong. Weeks later another change, by the AI or a person, removes a check. Nothing records what the route was supposed to do, so nothing can say that something is missing.

How it works

  1. Record. When a route is written, a small .route.json sidecar next to it says what it should be: public, login-only or internal. Clear cases are saved silently; unsure ones ask you and default to secured.
  2. Compare. check reads the sidecar and the route code and reports where they disagree.
  3. Catch. On a pull request, it flags an authentication check that was removed from a protected route, or a sidecar that was quietly weakened.

Catches drift

Intent says protected, code shows no authentication check, or a pull request removed the one that was there.

Catches downgrades

Flags a pull request that lowers exposure, or removes a gate, rate limit or network restriction from a sidecar.

Verifies the running app

Sends credential-free requests to a local or staging app. A protected route that answers 200 is reported as a gap. Safe methods only by default.

Guards admin pages

An extra gate (SSO, MFA or a passphrase of 8+ characters), a network restriction, and no links or sitemap entries unless you approve.

Catching a removed check

$ security-sidecar check . --base origin/main --format github --strict
::error file=app/api/orders/route.ts,title=auth-removed::an authentication
check present at origin/main is gone from this route, but its sidecar
says it must be protected. Restore it, or change the recorded intent

The finding shows up as an annotation on the pull request and fails the job. Detection is text matching for common patterns, so expect misses.

Generated from the examples/sample-api folder in the repository. /api/exports is recorded as protected, but no authentication check is visible in its code, so it is listed as a gap.

A sidecar

app/api/orders/.route.json
{
  "version": 1,
  "mode": "annotate",
  "route": "/api/orders",
  "methods": {
    "GET": {
      "exposure": "authenticated",
      "cache": {
        "policy": "no-store"
      },
      "indexing": "noindex"
    }
  },
  "reason": {
    "source": "heuristic",
    "rule": "path-api"
  }
}

This is the file save writes for a typical API route. It is a small file, reviewed in the diff like any other.

Install

/plugin marketplace add zafrem/route-protection-intent
/plugin install security-sidecar --marketplace zafrem/route-protection-intent

Installed straight from GitHub (the repo is its own marketplace). It is not in Anthropic's official plugin directory, so read the code before installing. Current release: v0.1.3.

Then check a project: /security-sidecar:check. The CLI is bundled and needs only Node 18+.

Good to know

  • Enforcement output supports Nginx, Next.js and Cloudflare. Next.js is the only framework tested end to end. Routes are also read for JS/TS, Python, Go, Java/Kotlin, C#, Ruby, PHP, Rust, Elixir, Swift and Dart, but those patterns were checked on small snippets, not real projects, and router mount prefixes are not resolved.
  • security-sidecar spec openapi.json compares an OpenAPI (JSON) document with the recorded protection and lists disagreements.
  • Authentication detection and the link scan are text matching, so expect misses and some false positives. If a check lives in middleware or a gateway, record it in enforcement.via.
  • reason.source: user is a convention an agent could forge, so review sidecar changes in pull requests.
  • This is one layer, not a security architecture. See the architecture guide for what has to exist underneath: central authentication, per-record authorization, a separate admin plane and a test that fails when protection is removed.
  • For secure-coding rules and linting, rely on /security-review and tools like Semgrep or ESLint security rules.
